# Auditoría técnica y legal — 5 de septiembre de 2026

Alcance: determinar si `Dashboard Uso APIs` (rama `main`, versión `0.2.2`) es
utilizable en cualquier sistema Windows sin riesgos de funcionamiento o de
seguridad, y producir un plan de acción accionable.

## Veredicto

**Puntuación: 66/100 — Riesgosa.**

La línea base `0.2.2` (último commit `f211c7c`) es sólida y cumple casi todas
sus propias afirmaciones: DPAPI, broker con token, renderer sin secretos,
fuses endurecidos, 50/50 tests, lint, typecheck y build correctos. Sin embargo,
**el árbol de trabajo actual NO debe considerarse listo para distribuir**, por
tres motivos combinados:

1. Hay **WIP sin commitear** que contradice el modelo de seguridad documentado
   (perfil de navegador persistente sin cifrar con sesiones reales).
2. El pipeline **CI fallaría hoy**: `npm audit --audit-level=high` encuentra
   `fast-uri` (high) y `@xmldom/xmldom` (moderate), mientras la documentación
   declara "0 vulnerabilidades".
3. Existen **scripts sueltos sin revisar** que bajan defensas (instalación de
   una CA raíz autofirmada) o matan procesos por nombre.

## Nivel de confianza y puntuación

- Tope `84`: no hay pruebas E2E del camino crítico (instalación → bandeja →
  widget → dashboard loopback → login web).
- Tope `69` por CI no verde y por secreto de sesión persistente en claro en el
  working-tree (`browser-profile`), aunque hoy no esté en HEAD ni empaquetado.

## Hallazgos

### Bloqueantes (corregir antes de distribuir)

**B1. Perfil de navegador persistente en claro (contradice el modelo).**
`lib/playwright-browser.server.ts` añade `launchInteractivePersistentContext()`,
que usa `chromium.launchPersistentContext(userDataDir, …)` con
`%LOCALAPPDATA%\Dashboard_Uso_APIs\browser-profile`. Ese perfil guarda en disco,
sin cifrar, cookies/tokens de sesión reales (Google OAuth, OpenAI, DeepSeek,
Anthropic). Contradice ARCHITECTURE.md, SECURITY.md y README ("contextos
efímeros, sin perfil persistente"), y la ruta ni siquiera coincide con
`.browser-profiles/` (ignorado). Si se publica, el usuario deja una sesión
capital en claro.

- Decisión obligatoria: o se conserva el contexto efímero, o el perfil se
  cifra/aisla y se documenta. Nunca publicar sesión persistente en claro.

**B2. Vulnerabilidades en lockfile y CI no verde.**
`npm audit` actual: `fast-uri` (high, SSRF vía IPv6/percent-encoding/host
confusion) y `@xmldom/xmldom` (moderate, inyección de XML). Ambas son
transitivas de las `devDependencies` (electron-builder), no llegan al usuario
final, pero `ci.yml` ejecuta `npm audit --audit-level=high` → falla.
`Docs/PROJECT_STATUS.md` y `PROJECT_CLOSURE.md` declaran "0 vulnerabilidades":
la afirmación quedó obsoleta.

**B3. Scripts sin revisar y sin documentar.**

- `arrancar-widget.bat` / `arrancar-widget.vbs`: matan **por nombre**
  `Dashboard Uso APIs.exe` con `taskkill /F /IM … /T` y arrancan `npm run
electron:dev` desde el path UNC/NAS, que como se comprueba abajo **no
  funciona** (`CMD.EXE … No se permiten rutas UNC`).
- `scripts/create-self-signed-cert.ps1`: instala el certificado autofirmado en
  `Cert:\CurrentUser\Root` (raíz de confianza) "para evitar SmartScreen".
  Contradice SECURITY.md y PROJECT_CLOSURE.md ("la firma autofirmada no aporta
  reputación; no crear exclusiones"). Baja defensas en la máquina.
- Ninguno está en Git, ninguno está revisado. No deben formar parte del
  repositorio ni de la distribución.

### Mejoras de alto valor

**B4. Sin pruebas E2E del camino crítico.** Solo hay 50 tests unitarios. Añadir
un smoke E2E (Playwright) que valide: instalación/portable → tray → widget →
`GET http://127.0.0.1:<puerto>` → 200 → renderizado de los cuatro proveedores →
launch de `browser-login`.

**B5. Sin health check.** No existe un endpoint de salud. El tray/poller depende
de `probePort`; un `GET /api/health` que compruebe broker + configuración daría
diagnóstico accionable en fallo.

**B6. Formato y trazabilidad.** No hay formateador (Prettier/Biome). Existen
avisos `CRLF will be replaced by LF`. Definir un formateador y un `pre-commit`
de formato.

**B7. Dureza de rutas.** `next.config.js` fuerza `WATCHPACK_POLLING` con
`process.cwd().startsWith('Z:')`: el punto de montaje del NAS no es siempre `Z:`,
y el build/CI en Windows no lo necesita. Detectar UNC/SMB de forma genérica
(`\\` o `//`).

**B8. Artefactos y datos reales en disco.**
`build/standalone-bundle/standalone/.env` y `scratch/deepseek-dump.json`
existen localmente (ignorados por Git, correcto). `deepseek-dump.json` puede
contener datos de sesión reales: conviene borrarlos del checkout para no
exponerlos ante filtraciones del disco.

**B9. `next-env.d.ts` versionado con referencias a `.next/dev/types/*`.** Es
autogenerado; al regenerarse con Next 16.3 introduce referencias a un artefacto
de build. Revisar si debe versionarse así o regenerarse limpio.

### Fortalezas verificadas (no piden acción)

- `GET /api/keys` devuelve solo `configuredIds`; PUT/DELETE validan IDs.
- `electron/lib/credential-store.js` falla de forma segura si
  `safeStorage.isEncryptionAvailable()` es falso; escribe temporal y renombra.
- Broker en loopback con bearer token aleatorio por env; el servidor se ejecuta
  con `utilityProcess.fork`, `runAsNode` y demás fuses deshabilitados.
- No hay secretos en Git, `.env.example` no tiene valores, `.gitignore` cubre
  `.env`, `build/`, `scratch/`, `browser-profiles`, certificados y `Thumbs.db`.
- Datos del usuario ligados a DPAPI; sin telemetría a nubes de terceros.
- Lint, typecheck, 50/50 tests y `next build` correctos en copia NTFS local.

## Legal y cumplimiento

- **Licencia MIT** presente, autor y repo URL coherentes (Zambudio). Correcto.
- **Terceros**: hay un clon `claude-usage-widget-main/` (proyecto ajeno) en el
  NAS, ignorado por Git y NO incluido en `electron-builder` (`files` /
  `extraResources`), por lo que no se redistribuye. Recomendado: eliminarlo del
  checkout para evitar confusiones de licencia o si se derivó cualquier
  fragmento de él, acreditar la autoría.
- **ToS de proveedores**: la app automatiza la consola web del propio usuario
  (ChatGPT/OpenAI login, DeepSeek scrape, Claude web, OAuth de Google). Esto
  puede incumplir los ToS y activar anti-bot/bloqueo de cuenta. Es un riesgo
  inherente ya documentado ("los endpoints internos pueden cambiar"), pero debe
  mantenerse explícito en README/PROVIDERS.
- **Privacidad**: no hay subida a nubes de terceros; credenciales cifradas con
  DPAPI ligadas al usuario. Bonito perfil de privacidad.
- **Distribución**: la firma es la deuda legal/trust bloqueante (unsigned →
  SmartScreen/EDR). La vía correcta es certificado reconocido desde CI, nunca
  autofirmado.

# Plan de acción

Orden por prioridad. Cada ítem indica criterio de aceptación.

### Fase 1 — Seguridad e higiene (bloqueante)

1. **Decidir el modelo de sesión web y revertir o cifrar el perfil persistente.**
   - Aceptación: no queda `launchPersistentContext` con perfil en claro sin
     cifrar; el comportamiento documentado de "contextos efímeros" se respeta o
     se actualiza la documentación y se cifra/aisla el perfil.
   - Acción: en `lib/playwright-browser.server.ts`, revertir a
     `launchInteractiveChromium()` efímero (estado HEAD) o mover el perfil bajo
     el almacén cifrado y documentar el cambio.

2. **Retirar scripts sueltos sin revisar.**
   - Eliminar `arrancar-widget.bat`, `arrancar-widget.vbs`,
     `scripts/create-self-signed-cert.ps1` del checkout, o moverlos a
     `Docs/` como referencia + explicitar que no se distribuyen (sin auto-signar
     raíces ni `taskkill` por nombre).

3. **Limpiar artefactos y datos reales del disco.**
   - Borrar `build/standalone-bundle` y `scratch/deepseek-dump.json` /
     `scratch/*` del checkout (regenerables/ignorados, y el dump puede tener
     datos de sesión). Confirmar que siguen en `.gitignore`.

4. **Actualizar dependencias y lockfile.**
   - `npm audit fix` para `fast-uri` y `@xmldom/xmldom`, o pin de versión
     compatible. Verificar `npm audit --audit-level=high` en 0 high.
   - Nota: ambas son `devDependencies` (empaquetado), no llegan al runtime.

5. **Reactivar/purgar afirma ciones obsoletas de la documentación.**
   - En `Docs/PROJECT_STATUS.md` y `PROJECT_CLOSURE.md`: reemplazar "0
     vulnerabilidades" por la evidencia actual y registrar el WIP pendiente.

### Fase 2 — CI y recurrencia

6. **Confirmar el estado real de GitHub Actions** en `main`; si está roto por el
   `npm audit`, arreglarlo en el mismo commit que el punto 4.

7. **Reemplazar el `WATCHPACK_POLLING` atado a `Z:` por detección genérica
   de UNC/SMB** en `next.config.js`.

8. **Decidir sobre `next-env.d.ts`**: regenerarlo limpio o eliminar las
   referencias a `.next/dev/types/*`.

### Fase 3 — Calidad y pruebas

9. **Añadir formateador** (Prettier o Biome) y hook de formato/`--check` en CI.

10. **Añadir smoke E2E** (Playwright) del camino crítico:
    - `GET /api/health` → 200;
    - tray → widget visible;
    - dashboard `127.0.0.1:3000` → cuatro proveedores renderizados;
    - flujo `browser-login` abre navegador y captura snapshot sin secreto.

11. **Añadir `GET /api/health`** (loopback) que compruebe broker + configuración
    y alimente el diagnóstico del tray.

### Fase 4 — Legal y distribución

12. **Eliminar `claude-usage-widget-main/`** del checkout o documentar licencia
    y autoría del fragmento derivado.

13. **Revisar/actualizar el aviso de ToS** en README/PROVIDERS: mencione que la
    automatización de la consola web puede violar términos del proveedor.

14. **Avanzar la firma crítica**: certificado reconocido (o Azure Trusted
    Signing) + secretos `WIN_CSC_LINK`/`WIN_CSC_KEY_PASSWORD` + release desde
    tag + timestamp + `SHA256SUMS.txt` + prueba en máquina limpia. Mantener
    "autofirmado = laboratorio, nunca release".

15. **Pasar de nuevo los criterios de validación**:
    `npm ci && npm run check && npm run build && npm audit --audit-level=high
&& git diff --check` en copia NTFS, y registrar en `Docs/PROJECT_STATUS.md`
    lo realmente validado.

> Nota de entorno: ninguna comprobación de `npm` puede ejecutarse desde la ruta
> UNC del NAS (`CMD.EXE … No se permiten rutas UNC`). Todas deben correr en una
> copia NTFS local (p. ej. `%LOCALAPPDATA%`), tal como documenta AGENTS.md.
